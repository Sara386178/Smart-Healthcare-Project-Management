# Demonstration test cases

Run from a fresh database so the seeded values match the expected results. Record the actual result during the live demonstration.

| ID | Scenario and steps | Expected result | Actual result |
|---|---|---|---|
| TC-01 | Launch the app for the first time and open Overview. | One project, eight activities, eight requirements, one pending change, three defects and three risks load from SQLite. Approved budget is PKR 5,000,000. | Verified: dashboard displayed PKR 5.0M, CPI 0.85, SPI 0.75 and two open critical defects; the seeded registers were visible in Scope & WBS. |
| TC-02 | Open Scope & WBS. | Six baseline requirements show Approved/in scope. AI diagnosis and mobile app are Pending and excluded from the approved scope. WBS shows activities grouped under three phases. | Verified: six baseline requirements were in scope, both CR-001 requirements were Pending, and WBS showed all three phases. |
| TC-03 | Approve CR-001 from Overview or Scope & WBS. | The transaction approves CR-001 and the two related requirements, adds the AI/mobile work package, changes budget to PKR 5,800,000 and moves deadline from 23 Nov to 14 Dec 2026. Repeated approval has no further effect. | Verified in isolated browser session: approved CR-001; both linked requirements became Approved, activity 4.1 appeared, Overview showed PKR 5.8M and the 14 Dec 2026 deadline, and Schedule & team showed activity 4.1 with the approved deadline. |
| TC-04 | Open Cost & EVM on the fresh seeded database. | PV is approximately PKR 4,080,175; EV is PKR 3,063,400; AC is PKR 3,600,000; CPI is approximately 0.85 and SPI approximately 0.75. Cost and schedule warnings are visible below the 0.90 threshold. | Verified in Chrome: PV PKR 4.1M (exact PKR 4,080,175.44), EV PKR 3.1M (exact PKR 3,063,400), AC PKR 3.6M, CPI 0.85 and SPI 0.75; both warnings displayed. |
| TC-05 | Update an activity to 70% progress and PKR 300,000 actual cost. | The record persists after refresh/relaunch and PV/EV/AC/CPI/SPI recalculate from activity data. | Verified: updated activity 3.2 to 70% and PKR 300,000; EV recalculated to PKR 3.3M, AC to PKR 3.9M, CPI to 0.85 and SPI to 0.81. Values remained after browser refresh (IndexedDB SQLite). |
| TC-06 | Enter activity progress above 100%, below 0%, or negative actual cost. | Validation rejects the values and shows an error; stored activity values remain unchanged. | Verified: 101% progress was rejected with a validation message and the saved 70% / PKR 300,000 values remained unchanged. |
| TC-07 | Add a requirement and leave it Pending. | New requirement appears in the register but is not counted as approved scope until approved. | Verified: added “Demo requirement test”; it remained Pending and outside approved scope. Changed priority to Could have and confirmed it persisted. |
| TC-08 | Resolve one critical defect and revisit Overview. | The unresolved-critical count decreases by one; defect status remains saved. | Verified: resolved the appointment double-booking defect; unresolved critical count changed from two to one. |
| TC-09 | Change a checklist result and add a risk with response. | New selections are reflected in the quality view and the report snapshot. | Verified: checklist row changed from Fail to In progress. Added “Demonstration integration delay” at likelihood 3 × impact 3 with response and owner; it appeared in the risk register. |
| TC-10 | Reject a pending change request. | Request becomes Rejected; project budget, deadline, baseline requirements and activities remain unchanged. | Verified: added and rejected “Demonstration change request” with zero cost/day impact; it remained Rejected and did not alter the approved baseline. |
| TC-11 | Attempt project closeout while critical defects remain unresolved. | Closeout is blocked; no closure record is written and the project remains open. | Verified: closure was blocked with two open critical defects and no closure record was saved. After resolving one defect, one critical defect remains, so closure should still be blocked. |
| TC-12 | Resolve all critical defects, decide every pending request, then record project closure. | The closeout transaction writes an approver, date and summary and marks the project Closed. | Verified by automated SQLite test: blocked before all gates were clear; then saved the authorized approver and changed status to Closed. |
| TC-13 | Add an activity that names a nonexistent predecessor code; then add a valid milestone. | Invalid predecessor is rejected without saving; a valid activity keeps its owner, dependency and milestone flag. | Verified by automated SQLite test, including unknown code, malformed date, invalid progress/cost, then a valid dependent milestone. |
| TC-14 | Approve a new change request with cost and schedule impacts. | Budget/deadline are rebaselined and the approved change creates its own linked work package in the WBS. | Verified by automated SQLite test: CR-002 +PKR 100,000/+5 days moved budget to PKR 5.1M and deadline to 28 Nov; work package 4.1 was added. |
| TC-15 | Attempt to approve either CR-001-linked requirement before deciding CR-001. | The requirement stays Pending and cannot be approved independently; approving the change request approves its linked requirements in the same transaction. | Verified by automated SQLite test: direct approval was blocked; change approval then approved both linked requirements and added package 4.1. |
| TC-16 | Add, update, prioritize and approve a new requirement. | Requirement is initially Pending and excluded; its text and priority can be updated, and approval moves it into scope. | Verified by automated SQLite test: created, edited to Should have, and approved “Audit export and review”. |
| TC-17 | Record a risk and checklist result; submit invalid severity, score and result values. | Valid entries persist; invalid values are rejected. | Verified by automated SQLite test: valid 3×4 risk and checklist update persisted; invalid risk score, severity and inspection result were rejected. |
| TC-18 | Reorder schedule records, edit a work package from its Gantt row, then set a cyclic predecessor. | Forecast finish is independent of database row order; valid changes persist; cyclic and unknown dependencies are rejected. | Verified by automated SQLite test; Chrome showed each Gantt work package as an accessible button and opening one displayed its edit form. |

TC-01 through TC-11 were exercised in Chrome during the earlier integration pass. CR-001 approval was repeated in an isolated browser session, and its changed Overview and Schedule were inspected; the primary demo database remains at the original pending-change baseline. The current `flutter test` suite contains 13 automated SQLite tests covering baseline data, exact EVM figures, timezone-stable forecasts, schedule editing and cycle prevention, CR approvals/rejections, requirements, validation, full quality-record editing, project status and closeout, plus one widget test for full-form validation. TC-12 through TC-18 were verified by automated database tests; they have not all been repeated as browser-driven form flows. The schedule interaction was additionally smoke-checked in Chrome: Gantt activities expose accessible buttons and open the edit form. The browser stores demo records locally, so use a fresh browser profile or clear the app site data to repeat seed-state checks. Existing screenshots document module views and Supabase project setup; they are saved evidence from the earlier integration pass, not a new authenticated browser walkthrough from this audit.
